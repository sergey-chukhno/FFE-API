# Feuille de Route v1.1 : Architecture Next.js, Scraping FFE Pur & Base de Données

*Auteur : Sergey CHUKHNO*  
*Date : Septembre 2026*  
*Statut : Document de référence strict pour les étapes 1 à 7*

---

## 1. Principes Directeurs & Engagements

1. **Suppression intégrale de l'API ChessXP** :
   La version v1.1 abandonne toute dépendance externe à l'API ChessXP (`ffe.chessxp.com`, clé d'API, etc.). La solution repose **exclusivement sur le moteur de scraping officiel de la FFE** (`echecs.asso.fr`).
2. **Conservation absolue de 100 % des fonctionnalités métier** :
   * Recherche nominale unitaire (nom, prénom optionnel).
   * Filtrage par club et par ligue.
   * Gestion complète des homonymes.
   * Insensibilité aux accents, tirets, espaces et à la casse.
   * Import et vérification Excel par lots (licences FFE ou nom/prénom).
   * Sécurité anti-XSS et assainissement des entrées.
   * Affichage paginé fluide (200 lignes par page) et numérotation `#`.
3. **Architecture de haute performance sans scraping à la volée** :
   Au lieu de scraper la FFE pendant que l'utilisateur attend, un **cron automatisé toutes les 24h** peuple une base de données PostgreSQL avec l'effectif de Marseille-Échecs. La vérification des licences pour un tournoi s'effectue alors en **moins de 50 millisecondes**.
4. **Validation séquentielle rigoureuse** :
   Chaque étape doit faire l'objet d'un plan d'implémentation détaillé soumis à la validation formelle de l'utilisateur avant son exécution.

### Étape 1 : Création de la Branche et Validation du Socle Initial
* **Objectif** : Repartir d'une base saine contenant uniquement le moteur de scraping historique, sans aucune trace de ChessXP.
* **Point de départ Git** : Commit initial `f1cb701`.
* **Branche créée** : `v1.1-nextjs-scraper`.
* **Livrables** :
  * Branche initialisée et propre.
  * Vérification du fonctionnement du moteur de scraping autonome.
  * Plan d'implémentation détaillé pour l'Étape 2.

---

### Étape 2 : Initialisation du Projet Next.js & TypeScript
* **Objectif** : Poser la structure d'application web moderne compatible Vercel.
* **Technologies** : Next.js (App Router), TypeScript, Tailwind CSS, Lucide Icons.
* **Livrables** :
  * Arborescence standard `src/app`, `src/lib`, `src/components`.
  * Configuration TypeScript stricte et ESLint.
  * Déploiement local validé sur `localhost:3000`.

---

### Étape 3 : Port du Moteur de Scraping en TypeScript / Node.js
* **Objectif** : Transformer les fichiers `.gs` historiques (`API_FFE_FETCH.gs`, `API_FFE_PARSE.gs`, `API_FFE_CLASSES.gs`, `API_FFE_UTILITIES.gs`) en modules purs TypeScript.
* **Changements clés** :
  * Remplacement de `UrlFetchApp` par `fetch` standard avec gestion des encodages (ISO-8859-1 / UTF-8 de la FFE).
  * Préservation de la normalisation (`removeAccents`, `normalizeForMatch`, `buildSearchVariantes`).
  * Tests unitaires automatisés validant que le scraping extrait les mêmes données qu'auparavant.

---

### Étape 4 : Modélisation et Intégration de la Base de Données (PostgreSQL)
* **Objectif** : Créer le schéma de persistance pour stocker l'effectif des clubs et l'historique des synchronisations.
* **Technologies** : PostgreSQL (Serverless via Neon / Supabase), Drizzle ORM ou Prisma.
* **Tables** :
  * `players` : numéro de licence (PK), nom, prénom, club, catégorie, af, élos, id FIDE, date de mise à jour.
  * `sync_logs` : horodatage, statut, nombre de joueurs synchronisés, durée en ms.

---

### Étape 5 : Cron Job 24h & Synchronisation Automatique
* **Objectif** : Scraper Marseille-Échecs une fois toutes les 24h en arrière-plan sans intervention humaine.
* **Technologies** : Vercel Cron (`vercel.json`) vers `GET /api/cron/sync-club`.
* **Fonctionnement** :
  * Déclenchement automatique chaque nuit à 03:00 UTC avec clé de sécurité `CRON_SECRET`.
  * Scraping complet des pages du club et `UPSERT` en base de données.
  * Aucun scraping synchrone lors des requêtes des utilisateurs.

---

### Étape 6 : Routes API Backend JSON
* **Objectif** : Fournir une API REST rapide, structurée et typée pour le client.
* **Points d'entrée** :
  * `POST /api/verify-batch` : Reçoit les participants de l'Excel, interroge la base PostgreSQL en une requête SQL (`WHERE licence = ANY(...)`), et renvoie les statuts en **< 50 ms**.
  * `GET /api/players/search` : Recherche nominale unitaire dans la base (avec option de scraping direct FFE pour les joueurs hors club).
  * `POST /api/admin/sync` : Déclenchement manuel de synchronisation par l'administrateur.

---

### Étape 7 : Interface Graphique Enrichie & Authentification Admin
* **Objectif** : Offrir une interface utilisateur moderne et sécuriser les actions d'administration.
* **Composants IHM** :
  * Zone de glisser-déposer de fichiers Excel (`.xlsx`).
  * Tableau paginé fluide (200 lignes par page) avec indexation `#`.
  * Bandeau d'état : date du dernier scraping et nombre de licenciés en base.
  * Authentification Admin (NextAuth.js / Iron Session) pour déclencher la synchronisation manuelle et gérer les paramètres.
